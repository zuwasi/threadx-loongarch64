# DEV-009: Memory functions convert `void *` parameters to object pointers

| Field | Value |
|---|---|
| Deviation ID | DEV-009 |
| Guideline | Rule 11.5 (Advisory): A conversion should not be performed from pointer to void into pointer to object |
| Parasoft checkers | MISRAC2025-RULE_11_5-b |
| Status | Draft (approval pending) |
| Scope | Port libc |
| Requirement(s) | LA-REQ-010 |

## 1. Locations

| File | Function or symbol |
|---|---|
| `ports/loongarch64/gnu/libc/src/tx_la64_string.c` | local `d`, `s`, `a`, `b` pointers in `memcpy`, `memmove`, `memset`, `memcmp` |

## 2. Reason for the deviation

The ISO C99 signatures of the four functions use `void *`, and a `void *`
cannot be dereferenced: implementing the functions requires converting the
parameters to object pointers. The conversions are to `uint8_t *` only, and
the access is byte-wise, which C permits on any object representation.

## 3. Risk analysis

- **Hazard:** a `void *` to object pointer conversion can lose
  qualification or produce an aliasing violation.
- **Why it cannot occur here:** all conversions target byte pointers,
  reading and writing one byte at a time; byte access is defined for any
  object type, and no wider or qualified access happens. `const`
  qualification is preserved on the source pointers. The functions have no
  other pointer arithmetic than indexing within `[0, n)`.

## 4. Compensating measures

- M6 unit tests (DEV-001 evidence) cover the four functions including
  overlapping `memmove` in both directions.
