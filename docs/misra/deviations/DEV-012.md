# DEV-012: Stack checking forces stack filling with `#undef`

| Field | Value |
|---|---|
| Deviation ID | DEV-012 |
| Guideline | Rule 20.5 (Advisory): `#undef` should not be used |
| Parasoft checkers | MISRAC2025-RULE_20_5-a |
| Status | Draft (approval pending) |
| Scope | Single location |
| Requirement(s) | LA-REQ-001 |

## 1. Locations

| File | Function or symbol |
|---|---|
| `ports/loongarch64/gnu/inc/tx_port.h` | `#undef TX_DISABLE_STACK_FILLING` under `TX_ENABLE_STACK_CHECKING` |

## 2. Reason for the deviation

ThreadX stack checking inspects the stack fill pattern, so the port must
guarantee that filling is active whenever `TX_ENABLE_STACK_CHECKING` is
defined. A user may define `TX_DISABLE_STACK_FILLING` on the command line;
the only way the port header can cancel that definition (without modifying
the kernel sources, which use `#ifndef TX_DISABLE_STACK_FILLING`) is
`#undef`. This is the upstream ThreadX port convention.

## 3. Risk analysis

- **Hazard:** `#undef` can remove a definition that later code still
  expects.
- **Why it cannot occur here:** the `#undef` appears once, in the port
  header, guarded by `TX_ENABLE_STACK_CHECKING`, before any code that uses
  `TX_DISABLE_STACK_FILLING`. The subsequent behaviour (fill pattern
  present when stack checking runs) is exactly the intent, and the
  regression suite exercises it in the `stack_checking` and
  `stack_checking_rand_fill` configurations (M4 results).

## 4. Compensating measures

- The two regression stack-checking configurations pass 96/96, which fails
  if the fill pattern is absent.
