# DEV-011: BSP API functions are referenced outside the compliance scan scope

| Field | Value |
|---|---|
| Deviation ID | DEV-011 |
| Guideline | Rule 8.7 (Advisory): Functions and objects should not be defined with external linkage if they are referenced in only one translation unit |
| Parasoft checkers | MISRAC2025-RULE_8_7-a |
| Status | Draft (approval pending) |
| Scope | BSP |
| Requirement(s) | LA-REQ-104, LA-REQ-106, LA-REQ-107 |

## 1. Locations

| File | Function or symbol |
|---|---|
| `bsp/qemu_virt/src/uart.c` | `bsp_uart_init`, `bsp_uart_putc`, `bsp_uart_put_dec` |
| `bsp/qemu_virt/src/timer.c` | `bsp_timer_init`, `bsp_timer_frequency` |
| `bsp/qemu_virt/src/power.c` | `bsp_test_report` |
| `bsp/qemu_virt/src/fatal.c` | `bsp_fatal_exception` |

## 2. Reason for the deviation

The BSP is a board-support package: its API is consumed by the application
and test layer - the bring-up test, the demo and the regression harness
(`test/regression/libc/src/printf.c` prints through `bsp_uart_putc`) - and by
assembly (`bsp_fatal_exception` is called from the exception vector in
`bsp_cpu.S`). The product-scope analysis builds only the kernel, port and
BSP libraries, so those references are not visible in it. The test-scope
analysis (`tools/misra.sh tests`) shows the C-side references.

## 3. Risk analysis

- **Hazard:** external linkage for a single-user function risks accidental
  redefinition and name collisions.
- **Why it cannot occur here:** the names are BSP interface names
  (LA-REQ-104/106/107) with unique definitions; the consumers are project
  code analysed in the separate test-scope scan; `bsp_fatal_exception` is
  invoked by the assembly vector, which whole-program C analysis cannot see
  but review and QEMU tests confirm (LA-REQ-106 fatal test).

## 4. Compensating measures

- The test-scope scan report lists the cross-module references.
- Every listed function is executed by a passing QEMU test (bring-up,
  demo or regression suite).
