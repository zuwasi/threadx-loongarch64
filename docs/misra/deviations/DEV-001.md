# DEV-001: Freestanding memory functions use standard library names

| Field | Value |
|---|---|
| Deviation ID | DEV-001 |
| Guideline | Rule 5.10 (Required): A reserved identifier or reserved macro name shall not be declared |
| Parasoft checkers | MISRAC2025-RULE_5_10-a, MISRAC2025-RULE_5_10-b, MISRAC2025-RULE_5_10-c (exact checker confirmed at first analysis) |
| Status | Conditionally approved by safety manager; technical lead approval pending (see section 5) |
| Scope | Two files |
| Requirement(s) | LA-REQ-010 |

## 1. Locations

| File | Symbols |
|---|---|
| `ports/loongarch64/gnu/libc/include/string.h` | declarations of `memcpy`, `memmove`, `memset`, `memcmp` |
| `ports/loongarch64/gnu/libc/src/tx_la64_string.c` | definitions of the same functions |

## 2. Reason for the deviation

The port is built freestanding (`-ffreestanding -nostdinc`) with no C library.
GCC requires `memcpy`, `memmove`, `memset` and `memcmp` to be available in a
freestanding environment: it can emit calls to them for structure copies,
structure initialisation and some loops, independently of the source code
(GCC manual, "C Language Standards"). The ThreadX kernel also calls `memset`
through `TX_MEMSET`. These calls only resolve if functions with exactly these
names exist, so the names cannot be changed.

## 3. Risk analysis

- **Hazard addressed by the guideline:** declaring a reserved name can conflict
  with the implementation's own definition, giving undefined behaviour, for
  example two different definitions, or a declaration that does not match the
  compiler's built-in assumptions about the function.
- **Why it cannot occur here:**
  - No C library is linked (`-nostdlib`), so there is no second definition.
    A duplicate would fail at link time, not at run time.
  - No C library header is visible (`-nostdinc`); the only declarations are in
    the port's `string.h`.
  - The prototypes match ISO C99 7.21 exactly, so the compiler's built-in
    knowledge of these functions agrees with the definitions.
  - The definitions are compiled with `-fno-tree-loop-distribute-patterns`, so
    GCC cannot turn their loops back into calls to themselves (infinite
    recursion). This is checked by inspecting the object file: it must have no
    undefined symbols.
- **Evidence:**
  - Link map: a single definition of each symbol (release build).
  - `nm -u` on `tx_la64_string.c.obj`: no undefined symbols (verified on
    commit 9880349).
  - Unit tests of the four functions, including overlapping `memmove` in both
    directions and zero-length calls (planned in milestone M6).

## 4. Compensating measures

- The build check above (`nm -u` is empty) becomes an automated CI step.
- The functions are byte-wise and contain no implementation-defined behaviour
  beyond the conversion in `memset`, which is explicitly masked to 8 bits.
